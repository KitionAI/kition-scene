# Scene kit design

`kit.scene` is Kition's 3D kit: a modeller in the spirit of Blender, built as a Kition kit.
It edits `.kscene` files in the page (WebAssembly engine in a worker, the kit's own editor in an
iframe) and serves the agent the same engine headless (`scene_*` tools). This note fixes what
the kit is, how it is built, and how far it matches its reference application.

## 1. Reference application and clean room

Blender is the reference application, the way Office is for Doc and Sheet and Photoshop is for
Photo: features, defaults, names, and keyboard habits follow Blender where they suit Kition, and
the kit's output is checked against Blender's. Blender's source is GPL and this kit is
Apache-2.0, so the rule is strict: the kit is written from Blender's documented behaviour and
observed output, never from its code (`AGENTS.md`).

`tools/blender-reference/reference.py` runs a local Blender in background mode and records facts
the tests use: the default scene, each primitive's counts and size with default parameters,
modifier and material defaults. `crates/formats/exchange/tests/blender.rs` runs Blender's own
glTF, OBJ, and STL importers and exporters against the kit's files when `KITION_BLENDER` names a
Blender executable.

## 2. Model

- **Units and axes.** Metres; Z up; right-handed. Rotations are XYZ Euler angles (X applied
  first), stored in radians and shown in degrees.
- **Scene.** Objects in a parent hierarchy; materials; a world (background colour and strength,
  and a shader group whose volume fills it); render settings (picture size, compositing, motion
  blur); the active camera. Ids are stable `u32`s, never reused.
- **Objects.** Location, rotation, scale, parent (with a parent-inverse matrix, so parenting
  never moves a child), hidden, material, modifier stack, and data: a mesh, a light (point, sun,
  spot, area; power in watts), a camera (lens and sensor in millimetres, clipping, orthographic,
  depth of field with a round or bladed, possibly anamorphic, opening), or an empty.
- **Meshes.** Positions, n-gon faces (counter-clockwise from outside), loose edges, and smooth
  or flat shading, smooth optionally by angle (edges sharper than it keep split normals in
  every viewport, render, and export; `object.shadeSmoothByAngle`, 30° by default). Triangles exist only for drawing and export (fan for convex faces, ear
  clipping for concave ones).
- **Modifiers** (non-destructive, in order): mirror, array, subdivision (Catmull–Clark with
  boundary rules), solidify, triangulate, weld, smooth. `modifier.apply` bakes one into the mesh.
- **Mesh operations** (edit mode): region extrude, per-face inset, subdivide, loop cut along an
  edge ring, merge at centre, delete vertices or faces, fill, flip, recalculate outside,
  translate and scale; selection is a vertex set (a face is selected when all its corners are).

## 3. File

`.kscene` is a ZIP: `mimetype` (stored first), `meta.json` (what identifies the content: format,
format version 1, kit, KDM and schema versions, document id), `content.kdm` (the scene's content:
the replica's sealed content snapshot, no history), content-addressed mesh and image data under
`blobs/<sha256>` (those the state references), and `editor.json` (view, selection, and current
frame). Writing the same parts gives the same bytes. Reading validates the archive, the content
against `meta.json`'s document id, referenced blobs, and scene and refuses damaged files. See section 7.5 for the replica's file boundary.

## 4. Engine and editor

- **The document is the viewport.** `width`/`height` are the editor's canvas size, set with
  `view.resize`. `render` and `render_area` sample one full software-rendered frame cached per
  revision (contract-exact through `kition_kit::raster`). `revision` moves with view changes;
  `dirty` only with scene changes.
- **Renderer** (`crates/render/raster`): z-buffered triangles with perspective-correct
  attributes and near-plane clipping, depth-tested lines and dots clipped to the picture, object
  and face id buffers for picking. Viewport shading: wireframe, solid (viewer-relative studio
  light), material (scene lights, Lambert plus a Blinn–Phong highlight from roughness, world
  ambient: a plain world colour lights diffusely and is reflected, so metals and gloss show it). Overlays: ground grid with coloured X/Y axes, selection outlines, origins, edit-mode
  vertices/edges/selected faces, camera/light/empty gizmos, and the dimmed outside of the camera
  frame. Final renders go through the scene camera at the render size with supersampling.
- **Commands** (`bindings/wasm/src/commands.rs`): every menu item and agent action, each with a
  JSON parameter schema, a menu path, a shortcut, and an availability rule. Scene changes run on
  the document and become one undo step; failures roll back.
- **Tools**: Select (click, Shift toggles, drag for a box), Move, Rotate, Scale (drag about the
  selection's centre in the view plane; Shift for fine steps, Cmd to snap), Loop Cut (hover
  previews the ring, click cuts). Navigation is the editor's: wheel zooms, middle drag orbits,
  Shift+middle drag pans, and a view widget aligns to front, right, top, or the camera.
- **Agent**: `scene_inspect` (objects with transforms in degrees, dimensions, materials,
  modifiers, mode, selection, view), `scene_commands`, `scene_run`; `check()` reports
  `scene.*` diagnostics with fixes (zero scale, inside-out meshes, no camera, no light, objects
  out of shot, ...). Objects can be named by id or by name in every command.

### GPU viewport

The editor draws the viewport with WebGL2 (`web/src/gl/`, `web/src/GlViewport.tsx`); the engine
keeps the scene and only describes it (`bindings/wasm/src/gl.rs`):

- **Protocol.** The `glScene` extra answers one frame as JSON: the orbit (and the engine's own
  view and projection matrices), the camera looked through (its view, WebGL projection, and
  render frame), shading, world, the world image's irradiance and turn, lights and each light's
  shadow map as the software viewport plans it, each drawn object (world matrix, material, a
  geometry `key`, paint, selection class, peer), the edit-mode selection, selected origins,
  depth-tested gizmo lines (cameras, lights, empties, lattices, bones and their custom shapes,
  fields, constraints), depth-tested flat `fills` (custom shapes' faces, drawn after the outlines
  and writing depth, as the software viewport does), lines and dots over everything (the armature
  edited or posed, curve and lattice points and handles, the text caret), and `supported`. Both
  viewports take an armature's lines, fills, and dots from one description
  (`kition_scene_raster::armature_marks`). The objects are the ones the software viewport draws
  (`kition_scene_raster::viewport_meshes`): sculpt mode's own mesh or multiresolution level,
  weight paint's mesh, and particles as the meshes made of them for the view. `glMesh(id,
  tangents)` answers one object's geometry as a binary buffer (`KGL1`: per triangle corner
  position, normal, UV, face index, optional tangents, optional paint — the mask or weight and
  the face set's tint — then the mesh's vertices and edges; hidden faces have no triangles),
  fetched only when the object's key changes. `glWorld()` answers the world image as linear
  floats (`KGW1`), fetched when the frame's environment key changes.
- **Drawing.** The software viewport's look, on the GPU: background gradient or the world image,
  studio light, material light with shadow maps (each light's depth pictures drawn into one float
  atlas from the engine's plans and looked up with the same bias, normal offset, and filter) and
  the world image's diffuse and reflected light, sculpt mode's clay (darker where masked, tinted
  by face set) and weight paint's colours, grid, wires, edit-mode faces, edges, and vertices,
  gizmos, points and handles, origins, two-pixel outlines (this person's selection and peers')
  from an id buffer, and the camera's frame with what is outside it dimmed. Lines are clipped at
  the near plane before upload (some GPUs drop a segment that crosses the eye plane whole), and
  depth-tested ones get the software viewport's slack (0.2 % of the eye depth), so the grid shows
  on a floor at the ground plane in both.
- **Navigation.** A drag or the wheel moves the view in the editor at once, with the engine's own
  orbit, pan, and zoom; the engine gets one `view.set` when the gesture ends, so it renders its
  software picture once, not per move.
- **The software viewport stays.** The engine still renders it under the GPU canvas (hidden):
  picking, the tools' overlays, the agent's pictures, and the headless kit use it. It shows
  instead whenever the GPU viewport cannot draw the state (more than eight lights in material
  view; shadows without float render targets), WebGL2 is missing or its context is lost, the GPU is emulated on the CPU (SwiftShader blocks the page for each
  frame), or `localStorage['kition.scene.gl']` is `off`.
- **Numbers** (`web/tests/gl-bench.mjs`, Chromium on an Apple M1 Max, 1440 × 900 at DPR 2, a
  102,412-triangle sphere): 2.6 ms per finished GPU frame (0.35 ms of it on the CPU), every orbit
  move drawn; the software path shows a picture every 139 ms. The GPU picture is within 0.5 to
  2.6 levels (mean per channel) of the software one at the same view; the web flow compares them
  in every state the GPU once left to the software viewport (point, spot, and sun shadows, a
  world image, a camera's view, sculpt masks, face sets, hidden faces, and multiresolution levels,
  weight paint, hair, bones, custom bone shapes filled and as wire, and curve points), within
  0.5 levels in Chromium and WebKit. The
  material view lights every pixel of a flat face in both (lights fall off and highlights move
  across it).

## 7. Collaboration

The document is a KDM replica (`kition-sdk` `session`, engine contract 2), schema `kit.scene`

existing type never gains a container field). People and agents edit one scene at once; every

| `NlaTrack` | `name`, `muted`, `solo` (boolean, optional), `strips` (list of `NlaStrip`) | |
| `Bone` | `name`, `data` (json), `constraints` (list of `Constraint`) | |
| `Action` | `name`, `channels` (list of `Channel`) | |
| `KeyingSet` | `name`, `paths` (json) | |
| `NodeGroup`, `Node`, `Link` | a group's `key`, `name`, `tree`, `inputs`, `outputs`, `nodes` (list of `Node`), `links` (list of `Link`); a node's `key`, `kind`, `location`, `values` (map) | |
| `Image` | `hash` (the SHA-256 of its bytes), `name`, `format`, `bytes` (blob) | Images are content-addressed: the same picture added twice is one record. |

Choices:
- **Geometry is a blob.** A mesh's positions, faces, loose edges, UVs, seams, pins, vertex
  groups, shape keys, and shading are one content-hashed blob (`mesh_blob`, the `.kscene`
  mesh buffer with a JSON tail). An edit-mode operation replaces the whole blob in one register,
  so two people editing the same mesh resolve to one of their meshes, never a mix that breaks
  faces; two people editing different meshes never meet.
- **Stacks are lists of records.** An object's modifiers, constraints, particle systems, NLA
  tracks (and each track's strips) and an armature's bones (and each bone's constraints) are
  records of their own in an ordered list (`held.rs`): two people adding to one stack, or
  editing two items of it, both keep their edits. An item's settings are one `data` register:
  they depend on each other (a modifier's operand, a bone's parent).
- **Animation lives with its target.** An object's keyframe channels are `Channel` records in its
  `animation` list, a material's in the material's, an action's in the action's; each channel's
  keys (with its driver and F-curve modifiers) are one register. Two people keying different
  properties of one object both keep their keys; two keying one property at once end with one
  channel holding both people's keys. An object's NLA tracks are its `nla` list and the blend of
  its own keys its `nlaAction`; tweak mode (the strip, the action it plays, and the keys put
  aside) is its `tweak` register: tweak mode and its keys always come from the same person.
- **A 3D text's characters are text.** A text object's body is the `text` field of its record:
  two people typing in it at once both keep their typing.
- **The current frame is session state.** Each person scrubs on their own; it is saved with the
  editor state, not in the replica. Animated properties hold values evaluated at the local frame,
  so the recorder writes the replica's stored values for them, never the evaluated ones; an edit
  of an animated property without a key stays local until the frame changes, as in the reference
  application.
- **Ids never collide.** Engine ids are minted from a range per actor (`ids::range`): 245,696
  ranges of 16,384 ids, so two sessions share one only by a chance of one in 245,696. The
  starter scene's ids are below every range, and the repair's (for a key a merge found twice)
  above.

### 7.2 Commands as transactions

Commands keep running on the engine's `Scene` (the view). After each command the bridge
(`write::write_changes`) diffs the scene before and after and writes what changed as one
transaction of the command's origin: created and deleted records, list moves, changed
registers, new blobs. The view is then the scene the command made. Undo and redo go through the
replica (contract 2 E14a): `edit.undo` takes back the last step of its scope (`person` or
`agent`), never a collaborator's, and the view is re-read from the replica. Remote changes are
imported the same way. A command that fails writes nothing.

### 7.3 Repair

After a merge (`SceneModel::validate`), deterministic for every replica:
- list entries of deleted records go, records no list names go, and a record listed twice
  keeps its first place (held records too, with what they hold);
- an item of a stack named like an earlier one (two people added one name at once) gets a name
  of its own (`Mirror.001`); two channels of one component (two people keyed it at once) become
  the first, with both people's keys (the first's on a frame both keyed);
- a parent, material, or scene camera that no longer exists is cleared (the camera falls back
  to the first camera in the list); a parent cycle made by two people parenting at once is
  broken at the object with the highest key;
- a material slot or the world image naming an image no record holds is cleared;
- a camera focusing on an object that no longer exists lets go of it (it focuses at its
  distance again);
- a bone drawn by an object that no longer exists (its custom shape) gets its octahedron back;
- an NLA strip whose action no longer exists (a peer removed or renamed it) goes; tweak mode
  follows its action's strip when a peer moved it, and when no strip plays that action any
  more it ends, the keys put aside coming back as the object's own;
- a constraint target or pole that no longer exists is cleared (the constraint stays, as in the
  reference application); a dependency cycle through constraint targets and parents is broken
  at the object with the highest key, whose constraints on the next object in the cycle go.

### 7.4a Presence

People in a co-edited scene see each other (Kit UI protocol section 7e, capability `presence`).
Each shares its selected objects as their KDM ids, the scene point under its pointer (the surface
there, else the ground plane) and, in edit mode, the mesh it edits and up to 256 of its selected
vertices (`presence.local`). The editor hands the host's `presence/peers` to the engine
(`presence.peers`): the renderer outlines each peer's objects in the peer's colour (never over a
locally selected object), and the engine places each peer's pointer, a name tag at the first
object they selected, and their vertices in this view's pixels for the editor to draw
(`presence.place` again after the view changes). The outliner badges each object with the people
who have it. The agent is a peer like anyone, recognised by its `agent` principal. Presence is
never saved, undone, or part of the replica.

### 7.5 File

A `.kscene` file (format version 1) holds the scene's content, not its history (kition-sdk data
model 7.3, rule M16b). It is a ZIP of `mimetype`, `meta.json` (`format`, `formatVersion`, `kit`,
`kdm`, `schemaVersion`, `docId`, and nothing a save changes), `content.kdm` (the replica's sealed
content snapshot: the state with its document id and object ids, and of the history only one
`system` change, the `content-seal`; no deleted or overwritten content, no person's or agent's
origin), `blobs/<sha256>` (every mesh and image the state references), and `editor.json` (view,
selection, the current frame; written only when the editor has a state). The history lives in the
host's history store (`snapshot()` of the live replica), never in the file. A file without
`content.kdm`, or whose content names another document than `meta.json`, is damaged; files of the
earlier layout (`replica.kdm` with its history) are not read.

Saving: every host calls `prepare_save` before `save`, which seals the live replica
(`KitSession::seal`, no edit and no undo step), and `save` writes `sealed_content_snapshot`; an
unchanged scene saves to the same bytes. One temporary fallback, for the kit editor until its
`@kition/*` release calls `prepareSave` (delete it once that release is in `web/pnpm-lock.yaml`):
a save of a replica nobody sealed writes the content of a copy sealed under an actor derived from
the version, and `mark_saved` imports that seal into the session.

Opening: a file opened alone is the same document with the same object ids and takes edits. A file
opened on the replica the host stored for it goes through `kition_kit::session::take_file`:
nothing when the store has the file's version, the file's changes when its history reaches the
store's version, and otherwise its state written by object id as one `system` `import`
transaction. A file another program saved while the scene is open is taken in the same way
(`reconcile_reread`).

Identity and forks (Kit Process Protocol 5.6, KitModel M7a; `kition_scene::SceneFiles`, served as
`document.identity` and `document.fork`): the file embeds its content replica, so a byte copy is
the same document. Its identity is the docId of `content.kdm`; an empty file has none, and other
bytes or damaged content are refused. A fork writes the SDK's copy under a new docId as
`content.kdm` (a copy's birth is its seal), sets `meta.json`'s docId to it, keeps only the blobs
its state references, and keeps `editor.json`, whose view and selection name objects by ids the
copy keeps.

### Rigid body motors

The Physics constraint type **Motor** independently enables linear and angular drives along
and about the constraint object's X axis. Both toggles default off, both target velocities and
maximum impulse controls to 1. Positive target velocity drives the first body relative to the
second; angular target velocity is in rad/s. Other degrees of freedom stay free, so a separate
hinge or slider can guide the motor. The linear impulse acts at the constraint pivot and can
produce torque when that pivot is offset.

The solver bounds each drive's accumulated impulse per substep by the maximum impulse control
multiplied by the substep duration, as observed in Blender. Solver iterations cannot multiply
that bound. The settings extend the existing object physics JSON register (KDM schema 6 stays
unchanged), survive undo and saved files, and invalidate a derived bake when edited. Commands
`physics.constraint.add`, `.set`, and `.connect` accept `type: "motor"`; `.add` and `.set` also
accept `linearMotor`, `angularMotor`, `linearTargetVelocity`, `angularTargetVelocity`,
`linearMaxImpulse`, and `angularMaxImpulse`. The English and Chinese Physics panels expose
these settings with the shared controls.

The clean-room reference script and observations are in
`crates/engine/physics/tests/blender/motors8.py` and
`crates/engine/physics/tests/fixtures/motors8-reference.json`. Offline checks compare evaluated
positions within 2 mm and orientation within 0.003 rad over the recorded frames; the optional
`KITION_BLENDER` run verifies the committed recording. This covers signed targets, reached
velocities, low caps, unequal masses, rotated axes and body frames, offset pivots, two-body
motion, both drives together, disabled controls and constraints, deactivation, and breakable motors. Motor breaking uses the
maximum individual drive impulse, including an exact threshold, rather than summing both drives.
Animated drive settings are not exposed. These measurements cover the recorded scenes and do
not claim general equality for arbitrary contact configurations.
